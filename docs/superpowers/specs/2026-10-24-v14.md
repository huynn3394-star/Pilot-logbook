# AviLog V14 — approved scope and implementation decisions

Baseline: AviLog_Flight_UI_V13_COMPACT_FULL_2026-10-23.zip (original ZIP retained).
User approved direct implementation in this conversation; deliver source ZIP, no deployment.
Keep V13 Compact appearance, Smart Scan V2, original ATPL content and dependencies.

1. Quick Entry searches only the active workspace. Same UTC date + normalized flight number (VN/HVN explicit alias) opens the existing flight rather than creating a duplicate. When user has other unsaved changes, offer a deliberate open instead. Historical flights supply route suggestions only: never registration, crew or Actual from another date. Multiple matches require selection. No network/data-provider integration.
2. Scan review compares old/new DEP/DEST and every timestamp with explicit UTC dates. The preview is a draft even when the existing flight is FINAL; no save/confirmation occurs automatically. Missing scanned values may be retained from the old flight, but are labelled missing and require review. Ambiguous matches require selection; unknown/invalid flight number never matches arbitrary records.
3. FINAL guard covers identity, route, aircraft, crew, role, allocations, Actual and evidence. Revised FINAL requires explicit permission and a reason. Record first confirmation and subsequent user edits as bounded, append-only before/after deltas, with image digest (not a second copy of bytes) and device timestamp. This is an application history, not a certified/tamper-proof logbook. Existing history is never silently truncated; reaching record/history limits blocks the write.
4. Optional v1 `logbook` metadata: SIC, PICUS, IFR, VFR, actual instrument, cross-country minutes; pilot's takeoffs/landings by day/night. Existing PIC/night fields remain. Blank means unknown; zero means explicitly zero. No PF→PIC, IFR→instrument, or automatic night computation. Each allocation is bounded by available block; actual instrument bounded by airborne. Category totals are not summed across overlapping axes. Preserve legacy SIC calculation but label it legacy; new V14 entries use explicit SIC.
5. Extend strict validation, atomic sync merge, JSON/CSV export and restore. Concurrent edits of an audited flight remain a reviewable conflict; no device-clock winner. Restore does not replace a live flight with retained audit history. New data is still private per UID.
6. Because Firestore currently rejects extra fields, add a public capability flag `AVILOG_LOGBOOK_V14_ENABLED` (default false). Guest mode supports V14 immediately. Signed-in workspaces stay in clearly labelled V13-compatible editing until owner deploys included rules and enables the flag. Existing V14 records become read-only when the flag is off, not stripped. Existing queued data, photos and ATPL are never reset. Update all devices; downgrade not supported after new metadata is used.

Checks: baseline unit suite, new unit tests (red then green), sync/backup tests, real editor browser interactions, layout 320/390/820/1440, static integrity comparison. Report physical-device/cloud/emulator limitations separately. Do not claim operational/legal certification.

## Implementation rulings from verification
- Rebuild the embedded Firebase workspace validator in Docker; startup fails closed when V14 is enabled with a stale SDK/source manifest. SDK hash stamps the service-worker cache so a subsequent build cannot retain the old bundle. The build pipeline is delivered but not run here (dependency download unavailable).
- Explicit conflict resolution selecting local data extends the server audit chain and records the reason; the local fork stays in repository recovery. Do not concatenate divergent audit entries as a single chronological chain.
- Cloud import of V14 guest/backup metadata is blocked before staging when the public capability flag is off; it is never stripped to force compatibility.
